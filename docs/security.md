# Security model

## Goals

- The DSH host is not reachable from the public internet.
- Only devices that completed QR pairing can reach the DSH UI.
- A device can be revoked individually, immediately.
- Secrets stay on the machine that owns them.
- The relay can be self-hosted by the same person who owns the DSH instance.

## Threat model

### Protected against

| Threat | Control |
|---|---|
| Network eavesdropping between phone and relay | TLS 1.2/1.3, HSTS, modern Caddy defaults |
| Network eavesdropping between DSH and relay | WSS over TLS |
| Random internet scanning / direct DSH access | DSH opens no inbound port; relay only exposes 80/443 |
| Unauthenticated relay users | device cookie required for every instance request |
| Pairing-code guessing | 10-char code, 120 s TTL, one use, per-IP and per-instance rate limit |
| Replay of a used QR code | code is consumed atomically and marked used |
| Stolen instance token reuse after rotation | token hash stored; rotate by updating the instance token |
| Compromised/lost phone | per-device revocation; revoke cookie on next request |
| DSH launch token leakage | token is used only on loopback by the plugin; it is never sent to the relay or phone |
| CSRF against relay endpoints | pairing is a top-level GET with a one-time code; cookie is `SameSite=Lax`; state-changing exchange is limited to the code |
| Token leakage in logs | URLs, cookies, and authorization headers are redacted; Caddy access logs are off |

### Not protected against

| Threat | Why |
|---|---|
| A malicious relay operator reading traffic | v1 terminates TLS at the relay, so the relay sees plaintext HTTP. Use a relay you control, or wait for the E2EE option. |
| A compromised DSH host | The plugin runs with the host's privileges; host compromise is out of scope. |
| A stolen unlocked phone | The stored device credential remains usable until the device is revoked. Add a device lock/biometric gate. |
| Denial of service on the relay | Single-process, in-memory rate limits. Put a WAF/edge limiter in front for hostile deployments. |

## Secrets

| Secret | Where it lives | Protection |
|---|---|---|
| Instance token | `~/.dsh/dsh-remote-tunnel/instance-token` (`0600`) | generated by `install.sh`; never committed |
| Device cookie | KMP platform private preferences, scoped by origin | OS app sandbox; relay validates the signed cookie/device row |
| Cookie signing key | relay `.env` (`COOKIE_SECRET`) | generated, `0600`; rotate to revoke all devices |
| DSH launch token | DSH process memory | used on loopback only |
| DSH browser cookie | plugin memory | minted per plugin process; not persisted by the relay |
| TLS private key | Caddy data volume | managed by Caddy |

The native client explicitly supplies device cookies in request headers. Browser
cookie flags do not encrypt native preference storage. Use HTTPS and OS device
protection; hardware-backed secret storage is not currently implemented.

The relay stores only a SHA-256 hash of the instance token and the pairing code.
Device cookies are signed with a relay-wide HMAC key; the device row is checked
on every request so revocation is immediate.

## Pairing

A QR code is a bearer secret for one pairing window. Treat a screenshot of the
code like a temporary password:

- Generate it only when needed.
- The code expires after 120 seconds and works once.
- The relay rate-limits failed redemptions.
- Revoke unknown devices from the DSH Plugins page.

For higher-assurance deployments, put the relay behind an identity-aware proxy
or require a VPN before pairing. A future version can add an explicit
"approve on DSH" step.

## Transport and headers

Caddy is the only public listener.

- TLS 1.2+ (TLS 1.3 preferred), automatic certificates.
- HSTS with `includeSubDomains`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- No Caddy access log by default, so pairing codes and URLs are not written to
  disk.
- The relay never logs request paths with query strings.

## Deployment hardening checklist

- [ ] Use a dedicated domain/subdomain for the relay.
- [ ] Point `*.relay.example.com` at the server so instance certificates can be
      issued on demand.
- [ ] Keep only 80/443 open; do not publish the relay port.
- [ ] Store `.env` and the instance token with `0600`.
- [ ] Back up the relay data volume and the DSH token file.
- [ ] Rotate the instance token if it may have leaked; restart the relay and
      update the plugin.
- [ ] Revoke lost devices from the Plugins page.
- [ ] Subscribe to security advisories for DSH, Caddy, Node, and the Android
      dependencies.
